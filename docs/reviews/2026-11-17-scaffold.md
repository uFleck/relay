## Deviations from the brief

- `ulid` 3.0.0 no longer has `Ulid::new()`; the compile error was fixed with
  `Ulid::generate()`.
- Added `Store::insert_status` and `Store::search_tasks` because the required
  test needs a status row and the FTS index needed verification. Added a
  WAL/foreign-key/user-version test.
- Added indexes beyond the five required:
  `project_statuses(project_id, position)`, `task_events(task_id, created_at)`,
  `task_links(task_id, kind)`, `conversations(peer_id, opened_at)` and
  `proposals(state)`.
- `analysis_jobs` is created before `proposals` so `proposals.job_id` can have
  its foreign key.
- CI runs `pnpm build` before `cargo check`; `generate_context!` needs `dist/`
  and the plain listed steps would fail without it.
- The release workflow uses a shared local composite action
  (`.github/actions/release`) so the self-hosted and hosted jobs do not
  duplicate steps. Two jobs, no matrix.
- Added `.gitattributes` (`* text=auto eol=lf`, binary icons).
- `version.ps1` warns when tagging a dirty tree; the README documents
  bump → commit → tag → push, because tagging before the commit points the tag
  at the previous commit.
- The machine's PowerShell execution policy blocks `powershell -File ...`;
  verification used `-ExecutionPolicy Bypass` and `pwsh`. The required
  `package.json` release script still says `powershell -File`; the README
  documents the workaround.
- `tokens-light.css`, font packages and the `hover.html` Vite entry are not in
  the scaffold.

### Risks

- The build portion is measured: 268.3s signed, on 2026-11-17. The full
  `release.ps1` path (install, `latest.json`, upload) is not measured yet. A
  version bump changes the local crate fingerprints; the warm `target/` helps
  dependencies but not the relink. Checkout and runner setup are outside the
  action's timer.
- A tag can publish code that CI never tested. A bad tag cannot be "unpublished"
  from apps that already updated; rollback is republishing the previous
  `latest.json` (PLAN §1.1).
- The prerelease gap is real once `0.x` betas start: `latest` would point at the
  beta.
- `gh release create` is not idempotent. A partial upload or a retry needs a
  manual delete, `gh release upload --clobber`, or a draft-first flow.
- The installer fallback (newest `.exe`) can hide a missing version match.
- The 420s failure happens after publish; the release is live when the job goes
  red.
- Secret pairing is unverified: the `Production` secrets must contain the
  private key for the committed pubkey, with its password if it has one.
  If the password is missing, the build can fail or prompt.
- `generate-signing-key.ps1` passes the password as a command-line argument
  during key generation; it is not printed, but it is visible to local process
  inspection.
- `version.ps1` can tag a dirty tree after only a warning; the tag may not
  contain the version bump.
- `app.security.csp` is `null`, and `core:default` grants a broad surface.
- No git remote is configured in this checkout, so a local release cannot
  resolve the GitHub repo until `origin` exists.

### Anything Opus should review

- Whether `--verify-tag` is sufficient, or the local script should also
  require `origin`/derive the repo and refuse a tag that is not at `HEAD`.
- The actual warm-build numbers: run a real `release.ps1` (or the self-hosted
  action) and compare the per-step table to the 5:00 budget.
- Whether a release must wait for green CI (tag → CI gate → release) or the
  current "tag builds immediately" model is accepted.
- Prerelease policy (`--prerelease`, `latest=false`) before the first `0.x`
  beta.
- Retry/partial-publish policy and whether to create a draft then publish.
- The secret/pubkey pairing and password handling in `Production`.
- `Cargo.lock`/workspace version handling after a bump.

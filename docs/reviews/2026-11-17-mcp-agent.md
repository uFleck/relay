## What changed

- **One server, two endpoints.** `127.0.0.1:38547`, `POST /mcp` (agent token) and `POST /mcp/analyst`
  (analyst token), JSON responses only, `GET`/`DELETE` return 405, bodies over 1 MB return 413. Methods:
  `initialize`, `ping`, `tools/list`, `tools/call`; anything else is `-32601`.
- **Fail loudly on the port.** `serve` binds exactly 38547. A taken port sets `McpStatus.error` ("port 38547
  is taken by another process; free it and restart Relay") and prints it once; the server never moves.
- **Auth.** Each endpoint has its own gate layer: `Host` must be `127.0.0.1:<port>` or `localhost:<port>`
  (403 otherwise, blocks DNS rebinding), a non-loopback `Origin` is 403, and the bearer is compared in
  constant time. 401 has an empty body and `WWW-Authenticate: Bearer`. The agent token cannot open
  `/mcp/analyst` and the analyst token cannot open `/mcp`. An empty configured token never matches.
- **Tokens.** `mcp-agent.token` and `mcp-analyst.token` in the app data dir, 32 hex chars from a UUID v4
  (122 random bits), created on first run and reused after. Never logged. `mcp_status` returns them so the
  setup sheet can copy the client config.
- **Agent tools** (thin over the store): `projects_list`, `tasks_list`, `tasks_get`, `tasks_search`,
  `tasks_changes`, `activity_list`, `tasks_create`, `tasks_update`, `tasks_claim`, `tasks_progress`,
  `tasks_link`, `tasks_add_requirement`, `tasks_ack_change`, `tasks_complete`, `tasks_release`,
  `proposals_list`, `proposals_submit`, `proposals_decide`, `sync_status`, `sync_now`.
  - `tasks_get` with `claimId` first checks that the claim owns the task (so a foreign claim is never
    extended), then heartbeats and returns the detail with that claim's `unackedChanges`.
  - `tasks_update` takes only `title, notes, priority, dueAt, statusId, position, archived` plus
    `expectedRev`; any other key is `invalid_args`, and a status whose category is `done` is `forbidden`
    ("use tasks_complete"). `tasks_create` refuses a done status too.
  - `tasks_link` and `tasks_add_requirement` (with `claimId`) return `unackedChanges`, as PLAN 3.4 asks of
    every claimant write.
  - `sync_status` returns `{"connectors": []}`; `sync_now` is `isError` with kind `not_configured`.
  - Results are `[{type: "text", text: <JSON>}]`; failures set `isError` with `{kind, message}` (plus
    `holder` on `claim_conflict`). Unknown tools are `-32602`.
- **Analyst endpoint.** `tools/list` shows only `jobs_get, jobs_complete, tasks_get, tasks_search,
  projects_list, tasks_create, tasks_add_requirement, proposals_submit`. Every other tool name is refused
  with `-32602` before parsing ("tool not allowed on the analyst endpoint: …"). Job-scoped tools require
  `jobId` (writes also `idempotencyKey`) and resolve the job's candidates first; with no job store yet
  that lookup fails with kind `job_store_unavailable`, so no analyst write reaches the store. The analyst
  `tasks_create` cannot set status, priority or due.

## Known risks

- **Analyst jobs are stubbed.** `jobs_get`/`jobs_complete` and every analyst write return
  `job_store_unavailable`. P3 must replace `job_candidates` in `analyst.rs` with a real `analysis_jobs`
  lookup and route `tasks_create`/`tasks_add_requirement` through `job_ops` before enabling them; the
  current write paths after the job check have no idempotency of their own.
- **`activity_list` is an adapter aggregate.** It reads up to 1000 tasks, keeps the 50 most recently
  updated, and merges their events in memory. Fine at today's size; a store query belongs in
  `relay-core` once the activity log (PLAN 4) exists.
- **Port conflict is fatal for MCP.** By design: the status shows the error and the app keeps running
  without MCP. There is no retry or "change port" control yet.
- **Token storage.** Tokens are plain files in the app data dir, readable by the same Windows user. They
  are local loopback bearer tokens, so this matches Hopper. `mcp_status` hands them to the frontend for
  the setup sheet; a later hardening could return them only on an explicit "copy" action.
- **`proposals_decide` is reject-only for agents (decided 2026-11-17).** A follow-up restricts the
  tool's schema to `reject` and refuses `approve` with `forbidden`; approve is human/UI-only, so an agent
  can withdraw a bad proposal but cannot bypass the review. Test:
  `agents_can_reject_but_not_approve_their_proposals`.
- **Store calls are synchronous.** Each tool call runs in `spawn_blocking`; the single SQLite mutex
  serializes them. Fine for local agents.
- **No session ids / client names.** `initialize` does not issue `Mcp-Session-Id`; the claim holder name
  comes from `tasks_claim.holderName` (default `agent`). Identity is the claim id, per PLAN 2.
- **Not wired yet:** `jobs_next`, per-client activity log (Settings → Agents), the "Executor reachable" dot,
  the setup sheet UI.

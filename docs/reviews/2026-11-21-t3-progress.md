- **What changed**
  - Migration `0011` adds `t3_progress` (last-good observation with branch, worktree, run identity, pending count, reply/error and a revision) and `t3_operations` (verbatim reserved draft, baseline run, delivery state and revision, with a partial unique index for one open continuation per Task).
  - Core `t3_progress` owns `RunStatus`, `ThreadObservation`, `SendOperation`, the observation decision and `confirms_send`. `preparing`/`queued`/`starting`/`running`/`waiting` map to **Dispatched**, and to **Needs answer** when the active run reports pending requests. A matching `completed` returns to **Returned**; `failed`, `interrupted`, `cancelled` and `rolled_back` become **Failed** with the run reason. Unknown statuses, idle without an attributable result, a terminal result for a non-matching run and a prior-run terminal result after an acknowledged queued send preserve the last known state; only a prior-run pending question is still surfaced. Replies are selected by assistant role and run id.
  - Store commits are fenced by Task openness (`dispatched`/`needs_answer`), bound-thread identity, observation revision and operation revision. PRs are upserted as read-only GitHub PR References by canonical identity and are never deleted when a later `show` returns a subset. Closure is explicit only, bumps the revision and fences open operations.
  - `t3_cli` decodes `thread show --json --messages 20` into the typed observation (including `pendingRequestCount`, `branch`, `worktreePath`, `runCount`, roles/run ids and bounded PRs) and `thread send <id> - --json` over verbatim UTF-8 stdin, classifying known rejections from lost responses. A response for another thread is never attributed.
  - The single Tauri worker polls bound open Tasks immediately and about every 3 s, reconstructs its watch set from SQLite on restart, allows one read per Task, caps child concurrency at 4, backs failed reads off to 30 s, and never replays a pending send or an initial dispatch. Failed reads keep the last good view and mark it stale with a Settings recovery path. PR merges and T3 settlement never close a Task.
  - Follow-up and Retry read the thread first; an already active run is observed and the draft stays unsent. The send is reserved before the CLI call; an acknowledged run id returns the Task to **Dispatched**. A lost response fences further sends; auto-confirmation needs exactly one run beyond the baseline with the exact message (modulo the CLI's trailing stdin newline). Otherwise the UI offers **Open in T3**, **Check again** and an explicit resend after the user confirms the first message was absent. A known pre-send failure keeps the draft for explicit retry.
  - The Task sheet shows branch/worktree, reply or error, linked PRs and their state, stale recovery, **Open in T3** for pending questions, **Follow up**, **Retry**, **Close as done** and **Close as cancelled**. Cancelling active work uses an in-app dialog that explains Relay stops tracking and links to the thread for stopping the run. `Needs you` grouping and the shared count are unchanged because they derive from stored Task statuses.
  - #36 predecessor gap: manual linking with a path selector now requires the entered thread id in `t3 thread list --project <frozen path> --base-dir <frozen profile> --json`, and `show` must agree with that row's thread and project id; zero, several or foreign rows keep the attempt fenced.

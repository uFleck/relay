# On-demand Slack sync (`Ctrl+Alt+S`)

**Status:** final
**Agent / model:** DeepSeek V4.1 Flash
**Commit(s):** `ed38883`

`docs/SLACK_SETUP.md`

## What changed

- `slack_sync_now` runs the same pull as the socket's catch-up: list the 1:1 DMs, read each channel
  from its stored cursor (14-day backfill on the first pull), store the messages, and hand the changed
  episodes to JEV.
- `Ctrl+Alt+S` (global), **Sync Slack now** in the tray, and **Sync now** in Settings → Slack all run
  it. Without a token, the hotkey and tray open Settings instead.
- The socket catch-up and a manual check share an atomic guard, so a reconnect cannot overlap a
  button press (both would call JEV for the same episode). A second press returns "A Slack check is
  already running."
- The hotkey run reports through a Windows notification; the Settings button shows the inline report
  (`5 conversations checked · 12 new messages · 3 episodes analyzed`). `slack://status` and
  `relay://change` are published either way.
- `catch_up` no longer clears a channel error immediately after publishing it: its final status update
  used to reset `error` to `None` unconditionally.
- The check reads only the user token; it does not open a socket and does not need the app-level token.

## Known risks

- **No real Slack token was available**, so `auth_test`, `list_dms` and `history` were not run against
  Slack through the new command. The client is covered by the `relay-core` mock tests; the loop is the
  same code that ran in the simulated-DM live test.
- The Windows notification was not exercised (the no-token path opens Settings instead).
- The tray item was not clicked; it calls the same `sync_in_background` as the verified hotkey.
- The shortcut is fixed at `Ctrl+Alt+S`. If another app owns it, Relay logs the registration failure and
  the tray/Settings paths still work.
- The first pull of a conversation stays a shadow backfill by design; a check on a fresh workspace stores
  answers without creating tasks.
- `analyzed` counts an episode even when `create_job` returns an existing job (a replay of the same
  watermark). It is a progress count, not a count of new JEV calls.

## Review checklist

- Does `run_sync` keep the cursor, pagination and duplicate-message behaviour of the old `catch_up`?
- Can the atomic guard leak or block the socket catch-up if `run_sync` panics?
- Does a manual check while the socket is live ever call JEV twice for the same watermark?
- Is the status update order safe (the closure reads `state.store` while `inner` is locked)?
- Should the hotkey be configurable, and does `Ctrl+Alt+S` collide with anything the user runs?
